# yfin-sveltekit

Turn a minified finance.yahoo.com SvelteKit build into readable code **without silently changing what it does**, and tell the user exactly how far that guarantee goes. The objective is simple: READABILITY of the important parts, end to end — from the build's self-description (what routes exist, which pages carry server loads, which files are the backbone) to the renamed, verified code. Builds drift daily (hashes change, files appear/disappear), so nothing is keyed to a hash or a node number, and it is NOT necessary to process the whole build — the parts that run on (nearly) every page are a small fraction of it and matter most.

## Ground rules (read first)

- **Only static work on files the user provided.** Never fetch, scrape or retry the live site (it answers 429 when hammered). Never run the code against the network: the runtime check blocks all non-local requests. Use only with the user's authorisation / the site's terms.
- **Scope: only `entry/`, `nodes/` and `chunks/`** (the `<site>/assets/_app/immutable` folder, or any folder above it: the scripts find it). Everything else next to it (other directories, `manifest.json`, service workers, non-JS files) is out of scope: never read, never copied, never in the output. Do not widen the scope and do not use a manifest or any other file to steer the work.
- **Credentials:** a build folder or upload may contain session, cookie or token files. Never open, print, copy, upload or package them (the scripts only touch `.js`/`.mjs`). Tell the user once that such files hold live credentials and should not be shared; exclude them from every output zip.
- **Never claim "100%".** Say what was proven and what was not (see "Final report"). Wakaru is a readability tool, not a semantics-preserving compiler; that is why verification is mandatory, not optional.
- Names are inference. Every semantic name is either B (confirmed from the function body / Svelte or SvelteKit source) or H (hypothesis). Say so.
- Answer in the user's language.

## Mental model

```
original build ──Wakaru (stage 1)──> readable but sometimes WRONG ──scan_hazards──> fallback list
        │                                                                              │
        └───────────────(same files, original code)────────────────────────────────────┘
                              │ stage 2: scope-safe renames + Svelte annotations + prettier (transform.mjs)
                              ▼
                        final tree ──verify_all──> verify_pair + ast_equiv + runtime_cmp (Chromium, offline)
```
Stage 2 only renames local bindings (Babel `scope.rename`); import/export specifiers never change, so module interfaces stay identical. Files the scanner flags skip Wakaru and are rebuilt from the original (still renamed + prettified). Third-party libraries that live inside `chunks/` (files named `*.min.*` / `*.worker.*`) never go through Wakaru; they are only renamed/prettified from the original. Verified on real builds: `entry/`, `nodes/` and `chunks/` import only each other (no import leaves the three folders), so the scoped copy is self-contained and the runtime check stays valid.

## Fast path: one command, any build (hashes change daily; nothing is hard-coded to a hash)
```
bash <skill>/scripts/setup.sh <W> && bash <W>/tools/selftest.sh          # once; selftest must PASS
nohup bash <W>/tools/run_auto_pipeline.sh <buildFolder> <outDir> 2 > <outDir>.log 2>&1 &     # typically 20-45 min on 2 cores (the runtime check is ~10 min of it); poll <outDir>/STATUS.txt (RUNNING <step> | DONE | FAILED <why>)
```
It runs every step below, builds the names map for THAT build (BUILD_ID from `entry/`, Svelte roles by code signature, Svelte and SvelteKit-client names from the official sources), and loops verification up to 3 rounds, moving runtime culprits to the fallback list. Result: `<outDir>/final`, `reports/ROUTES.md`, `reports/KIT_INTEL.md` (the decoded self-description: routes, server loads, matchers, hydration global, stale files), `reports/UNMAPPED_IMPORTS.md`, `reports/CHUNK_INDEX.md`, `VERIFICATION.md`, `FALLBACK_FILES.txt`; every `nodes/N.js` also gets a 3-line comment with the route(s) it is the page/layout of (a negative leaf = a page WITH a server load; node 0 = the implicit root layout when detected). On `FAILED` do not present anything as verified: read `work/` logs and use the manual steps. A `DONE` still only means the checks in "Final report" passed.

## Focused scoping: what to deobfuscate (readability first, coverage by choice)
SvelteKit pages do not exist in a vacuum: they inherit layouts in cascade, and `entry/app.<hash>.js` holds the family tree (the `dictionary`: route -> [leaf, layouts, errors]; a negative leaf = a page with a server load, and the root layout node 0 is implicit — see `references/kit-internals.md`). The master layout runs on nearly every page, and the chunks it imports are the code the user actually wants to read; every page node is a light leaf that only adds its own loaders. So do NOT treat the ~1000 files as a bag of loose things — pick the scope:
```
YFIN_ROUTES="@universal" nohup bash <W>/tools/run_auto_pipeline.sh <buildFolder> <outDir> 2 > <outDir>.log 2>&1 &   # the code that runs on (nearly) every page
YFIN_ROUTES="quote/"     nohup bash <W>/tools/run_auto_pipeline.sh <buildFolder> <outDir> 2 > <outDir>.log 2>&1 &   # one route family
```
`YFIN_ROUTES` picks the scope: `@universal` (the recommended default for this skill's objective) = the implicit root layout (node 0 — current builds: the kit client prepends it to every route and the dictionary NEVER lists it, so it is DETECTED from the kit client chunk, not counted by frequency) plus the layouts that run on >=95% of ALL routes, plus the entries and their import closure, no page nodes; a space-separated list of substrings matched against dictionary keys (`quote/` matches `/(app)/quote/[symbol]` and every sub-route) = route families; `*` or unset = the whole build. The selection is computed by `scripts/select_routes.mjs` (`scripts/scope_routes.sh` wraps it): seeds = the two entries + the union of the layouts of the matched routes (the backbone) + every matched route's page node (leaves; a NEGATIVE leaf = a page WITH a server load, node = `~value`, kept like any other leaf) + node 0 when detected as the implicit root layout; files = the static-import closure of the seeds + their `__vite__mapDeps` preload deps (parsed positionally from the nodes array — entries are `import(PATH).then(p=>p.X),__vite__mapDeps([...])`) + the dynamic imports of everything except `app.<hash>.js` (its dynamic imports ARE the route table — the filter replaces it). On a real build, `@universal` selects ~115 files (~5.8%: the root layout, the master layout, header, session state, global utilities, the SvelteKit client); `quote/` selects ~534 files (~27%) across 51 of the 219 routes; the rest is noise (news, mortgage calculators, quizzes, privacy pages) that is never read. Smaller scopes also run proportionally faster through Wakaru and the runtime check. Node numbers are NEVER hard-coded — the selection follows THIS build's dictionary (a renumbered dictionary picks the right files — regression-tested), and rare `nodes[i]` slots that import `chunks/*.js` (Vite fused the node into a chunk — seen on a real build) resolve correctly because the nodes array is parsed positionally. A folder holding leftovers of older builds (same node number, different hash — measured: 282 current node slots vs 564 files on disk) is fine — the stale files are ignored and counted in the report. The selection JSON also carries a `hubChunks` report (the chunks most imported by the current nodes, with `inSelection` flags): when a chunk "obviously runs on every page" but is NOT in the backbone — FooterV2 and loadMarketTime moved from the master layout to per-node imports between two real builds — the report shows the numbers instead of guessing, and a family scope pulls such chunks in transitively. The selection is guaranteed import-closed: the script exits 1 (refuses to scope) when a static import is missing on disk (incomplete download) or leaves entry/nodes/chunks. `--static-only` (flag of `select_routes.mjs`) drops the dynamic-import follow for an even tighter, still-closed set.
Read the map before cutting: `node scripts/kit_intel.mjs <buildFolder> <outDir>` (the pipeline does it automatically) writes `reports/KIT_INTEL.md` — all routes, which pages carry server loads and on which node file, the matchers (with localized route aliases), the hydration global `__sveltekit_<id>`, the build constant, stale-file accounting, and how many routes a naive `Math.abs` reading would misattribute (on a real build: 20). Every rule behind it is verified and evidenced in `references/kit-internals.md`. When the user hands over data payloads (a `__data.json`, or the array inside a page's inline hydration script), `node scripts/decode_devalue.mjs <file> [--node N] [--api-map reports/API_ENDPOINTS.md]` decodes the devalue wire format to readable JSON and can write a static inventory of every API URL/hostname found in the payload strings (the layout-2 payload carries the kit's master service table) — offline, user-provided files only.
Honest limits, all repeated in `VERIFICATION.md` automatically: the verification covers ONLY the selected scope (`@universal` = the code that runs on (nearly) every page, NO page nodes; a family = that family's backbone and pages); code that runs only on other routes is neither transformed nor verified; `app.<hash>.js` itself is always included whole (it statically imports only a handful of chunks); the per-route i18n XHRs and the webcore scripts (e.g. the real-time streamer) are outside `entry/nodes/chunks` and therefore outside this skill either way. When the user asks for readability of "the parts that go on every page", start with `@universal`; for "the code that runs on /quote/..." use the family; for the whole site, keep the default.

## Manual workflow (only to debug a FAILED run; exact commands in `references/workflow.md`)
setup + selftest -> `scope_build.sh <buildFolder> <W>/src` (use `<W>/src` as the build root below) -> `wakaru_run.sh` -> `scan_hazards.mjs` (its `.list.txt` is the fallback list) -> `make_map.mjs` (per-build names map: BUILD_ID from `entry/`, Svelte runtime roles by code signature, Svelte and SvelteKit-client names matched structurally against the official sources, see `references/naming-method.md`) -> `prescan_components.mjs` -> `run_transform.sh` (with `NAMES_MAP` exported) -> `apply_fallback.sh` -> `verify_all.sh`; on a runtime failure `rt_report.mjs --culprits`, add those files to the fallback list, re-apply, re-verify, until `OVERALL PASS` -> `reports.mjs`. Never "fix" a failure by editing a verifier or ignoring a diff. Check for `.map` files first: if the user has them, `wakaru extract` is the better path (untested here). The Svelte annotations assume Svelte 4; `detect_roles.mjs` says so explicitly (a `svelte5Suspect` note and a stderr warning) when it finds Svelte 5 runtime primitives instead of failing silently.

## Partial uploads (a few chunks instead of the whole build)
The scripts need the build folder (`entry/start.<hash>.js` + `entry/app.<hash>.js` with `nodes/` and `chunks/` beside it): the BUILD_ID guard, the name map and the runtime check all depend on it. Ask for the whole zip. If that is impossible, run only Wakaru + `scan_hazards.mjs` + prettier on the files given, use the original code for flagged ones, and state plainly that renames were not applied and nothing was runtime-verified.

Tool calls time out at ~10 min and the biggest chunks take minutes: always run stage 2 and verification in the background and poll with short commands.

## Final report (what to tell the user)

State: files processed/failed; how many came from Wakaru vs. fallback and why; each verification result with numbers (verify_pair, ast_equiv, runtime_cmp incl. components rendered); the known limits:
- runtime check loads every module, renders Svelte components with empty props and calls every exported plain function with synthetic arguments in both trees; it does not run the whole app with real data, interaction or network, and it cannot see inside closures/registered callbacks; modules that fail identically in both trees (e.g. missing `protobuf` global) pass trivially;
- Wakaru's rewrites in the non-flagged files are tested, not proven; `Function.length` may differ (info only in the scan);
- names are inference; unmapped imports remain (UNMAPPED_IMPORTS.md);
- files flagged as unsafe keep the ORIGINAL code (only renamed/prettified), so they are as readable as the original allows, not as Wakaru would have made them.
Offer the next step (map the most used unmapped exports; re-verify) instead of recapping the process.
