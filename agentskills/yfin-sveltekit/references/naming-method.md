# Naming method

Renames are LOCAL aliases only (`import { s as safe_not_equal }`). Import/export specifiers never change. Maps are keyed by (chunk base name, export letter); each entry is B (confirmed from body / Svelte or SvelteKit source) or H (hypothesis). Unmapped imports stay as their minified letters and are listed in UNMAPPED_IMPORTS.md.

## What is automated and what is by hand
`make_map.mjs` does, for the build in front of it: BUILD_ID from `entry/`, the Svelte runtime roles by code signature (`detect_roles.mjs`), every Svelte runtime export that matches the official Svelte source (`svelte_names.mjs`) and the SvelteKit client functions that match `@sveltejs/kit` (`kit_names.mjs`). Everything else (stores, session, feature flags, components, business logic) has no public source: add names by hand only when the function body proves them (B) or as a clearly labelled hypothesis (H). Helpers for manual work: `scan_imports.mjs <root> <counts.json>` counts imports per `chunk::export`; `dump_exports.mjs <chunk.js> <counts.json> <chunkBase> <out.tsv>` lists a chunk's exports with usage counts and code (most used first); `NAMES_MAP=<map> node validate_maps.mjs <orig>/chunks` checks a map (exports exist, names valid and unique). A hand-written map must export `BUILD_ID`, `ROLES`, `IMPORT_MAPS`, `LOCAL_MAPS`, `SVELTE_FRAGMENT_METHODS` (copy the shape of a generated `names_map.mjs`). If `.map` files ever ship, `wakaru extract` (untested here) may restore real names and sources, better than any inference.

## Using the official sources (the main lever)
Open-source parts of the build can be named from their real source, which is evidence rather than inference:
- **Svelte runtime** - automated: `svelte_names.mjs` matches each exported function by structural fingerprint (`shape_match.mjs`) against `svelte@<ver>` (default 4.2.19; the build only carries the major `"4"`, so a different minor can lower the match rate - try other versions with the 3rd argument). On real builds it names about 89 exports (two runtime chunks); in a comparison with hand-made names it agreed everywhere except one hand-made error (a person-assigned "B" is not infallible; a structural match is better evidence). Short/trivial functions (shape < 40 nodes) are not used because they are not distinctive.
- **svelte/store, svelte index** are included (writable, readable, derived, onMount...).
- **SvelteKit client** (the chunk that `entry/start.*.js` imports) - automated by `kit_names.mjs`: top-level functions are matched against every non-server module of `@sveltejs/kit` (`src/runtime`, `src/utils`; esbuild syntax-minified with `DEV=false`, `BROWSER=true` like a production build). The build does not state its kit version, so several are tried and the best is reported (the three builds tried: 2.8.x, about half of the functions; newer versions match fewer). Exported letters get the real function name, the rest become LOCAL_MAPS entries for that file; short/generic names get the file stem as prefix (`session_storage_get`). Public API names that differ from the internal function (`goto` vs `client_goto`) are NOT unified: check `references/svelte-structure.md`. Docs pages (svelte.dev/docs/kit) describe behaviour and public API names; they confirm hypotheses but are not code to match.
- App-specific code (stores, session, feature flags, components) has no public source: names stay H unless the body proves them.

## Roles instead of hard-coded chunk names
`transform.mjs` reads `ROLES` from the names map: `init` and `component_subscribe` ({chunk, export}) drive the Svelte component annotations. An optional `app_lib` role ({chunk, getStore, isFeatureEnabled, getSession, loadSession, loadStores}) names store/session helpers; nothing generates it (no public source), so add it by hand if you map those. A missing role disables only its annotations. `detect_roles.mjs` finds init / component_subscribe / safe_not_equal by code signature (chunk names and export letters differ in every build). Signatures can break if Svelte changes its compiled output: with Svelte 5 `detect_roles` finds nothing and the transform degrades to renames-only, which the verification still covers — and it now says so explicitly: chunks containing Svelte 5 runtime primitives (`$.template`/`$.state`/`$.effect`/`$.props`) with no Svelte 4 lifecycle signatures produce a `svelte5Suspect` note in the roles JSON plus a stderr warning.
